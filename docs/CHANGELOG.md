# CHANGELOG

vanilaChatbot의 변경 기록입니다. 최신 Loop가 위에 있습니다. 각 Loop의 자세한 측정·판단 근거는 [LOOP_LOG](LOOP_LOG.md), 현재 동작 명세는 [SPEC](SPEC.md)에 있습니다.

항목 읽는 법: **추가**(새 기능) · **변경**(동작이 바뀜) · **수정**(버그·보안 수정, 리뷰 지적 포함) · **신경 쓴 점**(설계할 때 일부러 고려한 위험과 대응) · **검증**(근거가 된 테스트·측정).

## 리뷰에서 잡은 것
리뷰는 구현한 세션이 아닌 별도 에이전트가 했습니다. Loop 19는 ponytail-review 지침으로 subagent 3명이 영역을 나눠 읽기 전용 복사본을 리뷰했고, Loop 23–30도 매 회차 새 에이전트에게 맡겼습니다(구현한 쪽의 결론은 주지 않고 대상과 방법만 줌). 지적은 Must / Should / Nice로 나눴습니다(Loop 23 첫 리뷰와 23.3은 등급 없이 적혀 있습니다). Loop 23부터는 새 회귀 테스트가 고치기 전 코드(또는 그 수정을 되돌린 코드)에서 실패하는 것까지 확인했습니다. Loop 24–30은 Must·Should가 하나도 나오지 않을 때까지 리뷰를 되풀이했습니다(24.4, 25.9, 26.3, 27.3, 28.3, 29.3, 30.4에서. Loop 31부터는 사용자 결정으로 Loop마다 1번 리뷰하고, 다음 Loop가 의존하거나 공유 서버의 다른 사용자에게 영향 주는 Should만 바로 고칩니다 "리뷰 루프 종료"). Loop 23은 처음에 "Must가 없으면 종료"가 조건이었습니다. 23.6에서 이 조건을 채웠지만 23.7에서 Must가 다시 나왔고, 23.8에서 다시 Must가 없었습니다. 23.9에서 사용자 결정으로 "Should가 없을 때까지"로 바꿨습니다.

### 특히 중요했던 지적
- **심볼릭 링크 바꿔치기로 호스트 파일에 닿음** (Loop 19): 호스트 쪽 파일 tool이 경로를 검사하고 여는 사이에 sandbox가 디렉터리를 링크로 바꾸면 호스트 파일을 읽거나 쓸 수 있었습니다(읽기 972/3000 성공). 19.1에서는 `git_commit`에서도 같은 일이 재현됐습니다. 파일 읽기·쓰기를 컨테이너 안(`docker exec`)으로 옮기고, git과 push는 `docker pause` 상태에서만 돌게 했습니다. 바꿔치기 도중 읽기 200·쓰기 50·커밋 20회에서 호스트 노출 0.
- **큰 출력 한 번에 서버 OOM** (Loop 19): 명령 출력과 `read_file` 결과를 서버 메모리에 전부 받은 뒤에 잘랐습니다. 출력은 스트리밍으로 앞뒤 5KB만 남기고 `read_file`은 20MB 상한을 뒀습니다. 300MB 출력에서 서버 RSS 증가 +0MB.
- **에이전트가 `.pth`를 심어 다른 코드를 가로챔** (Loop 23): 에이전트끼리 run 컨테이너를 같이 써서, `/tmp`에 `.pth`를 심으면 그 뒤에 도는 python(다른 에이전트, skill 스크립트)이 그 코드를 실행했습니다. 호출마다 새 컨테이너(`Sandbox.fresh()`)를 띄우고 `python -I`로 실행하게 고쳤습니다(`t_rogue_agent_is_contained`).
- **수정이 만든 호스트 탈출 구멍** (Loop 23.2): 23.1에서 run의 `outputs/`를 에이전트에 쓰기 가능하게 bind mount하도록 고쳤는데, `outputs`를 호스트 경로 링크로 바꾸면 다음 에이전트가 그 호스트 폴더를 읽고 쓸 수 있었습니다(비밀 파일 읽기 재현). bind mount를 없애고, 에이전트 outputs는 호출마다 따로 둔 뒤 일반 파일만 run 컨테이너 안에서 쓰게 바꿨습니다. 23.3에서 tmpfs와 tar 스트림으로 정리했습니다(`t_outputs_symlink_does_not_reach_host`).
- **위조·거대 tar 스트림으로 서버가 멈추거나 메모리 폭증** (Loop 23.4–23.7): 아주 큰 희소 파일 하나(run 쪽 4TB, 에이전트 쪽 4EB)로 서버 스레드가 멈췄습니다(이전 코드는 193초 뒤 실패). 300MB를 주장하는 헤더로 +1,146MB, 희소 맵으로 +431MB, 16KB 이하 pax 헤더 수천 개로 +1.3GB(40MB 스트림)가 늘었습니다. 보내는 쪽에서 `find -size`로 걸러 보내고, 읽는 바이트에 상한을 두고, pax 헤더와 희소 멤버는 읽기 전에 거부했습니다. 결과는 +0MB.
- **동시 요청으로 로그인 잠금 우회** (Loop 24.1): 잠금 확인과 실패 기록 사이에 해시(약 50ms)가 끼어 있어 잠금이 덮어써졌습니다. 16스레드로 20초에 약 230번 추측했고, 공격 중에도 맞는 비밀번호로 로그인됐습니다. 확인과 "시도 중" 표시를 한 락 구간에서 처리하게 했습니다(테스트에서 추측 140번 → 5번 이하).
- **이상한 비밀번호 하나로 계정이 영구 잠김** (Loop 24.2): 비밀번호 `"\ud800"`(합법 JSON)이 해시에서 예외를 내면 "시도 중" 카운트가 남았습니다. 5번이면 그 계정이 영구히 잠기고, 지어낸 이름 1만 개면 모든 새 로그인이 거부됐습니다. `surrogatepass`로 인코딩하고 시도 기록은 `finally`에서 풀게 했습니다(`t_odd_input_never_sticks`).
- **삭제된 계정이 살아남음** (Loop 24.3): `/password`가 확인한 뒤 무조건 upsert해서, 해시 두 번 사이에 관리자가 한 `remove`·`passwd`를 되돌렸습니다(10/10, 재설정 6/6). 확인한 해시가 그대로일 때만 바꾸고(`UPDATE … WHERE pw=?`) 아니면 409를 돌려줍니다.
- **Caddy 관리 API가 모든 로컬 계정에 열림** (Loop 25.2): `localhost:2019`로 아무 로컬 계정이나 TLS 종단 설정을 바꿀 수 있었습니다. caddy 계정만 쓸 수 있는 소켓으로 옮겼습니다(소켓 줄을 지우면 nobody가 200을 받는 것을 테스트로 확인). 25.3에서는 docker.socket이 다시 시작되면 렌더러·gateway가 Docker에 닿는 문제도 고쳤습니다.
- **SSH가 끊기면 설치가 중간에 멈춤** (Loop 25.5): 터미널 쓰기가 EIO로 실패해 `set -e`로 끝났고, EXIT trap도 echo가 먼저 실패해 되돌리지 못했습니다(25.3 테스트는 출력을 파일로 보내서 놓쳤습니다). pty를 열고 닫는 테스트로 재현했습니다. 전환 구간의 출력은 로그 파일로 보내고, trap이 되돌리기부터 하게 고쳤습니다.
- **한국어 locale·프록시 환경 변수가 있는 서버에서 설치 불가** (Loop 25.7): apt의 영어 출력(`Candidate:`)에 기대고 있어 한국어 locale에서는 "후보:"가 나와 매번 중단됐습니다. 상태 확인 curl은 `http_proxy`를 따라가서 첫 설치가 실패하고 업데이트는 매번 되돌려졌습니다. `LC_ALL=C`와 `--noproxy '*'`로 고쳤습니다(`t_korean_locale_and_proxy_env`).
- **쓰기 실패 때 기존 파일이 잘림** (Loop 26.1): 같은 내용을 다른 경로로 올리면 이미 있는 blob을 제자리에서 다시 썼습니다. 디스크가 가득 차면 기존 파일이 잘렸습니다("keep.bin was cut short" 재현). 이미 있는 blob은 다시 쓰지 않고, 새 blob은 임시 파일에 쓴 뒤 `os.replace`로 바꿉니다.

참고: 근거는 `docs/LOOP_LOG.md`(Loop 19, 23–27)와 커밋 `9d0a63a`, `4597c04`, `2d602b7`–`5d87006`, `052d2b1`–`c7bb9e1`, `1ec388d`–`7bb10cd`, `03ba995`, `196efd7`입니다. 기록에 없는 것이 두 가지 있습니다. Loop 19 기록에는 "고치기 전 코드에서 실패 확인"이 없고 "재현 스크립트로 확인, 회귀로 넣음"으로만 적혀 있습니다. Loop 23은 23.9에서 Should 1건을 고친 것이 마지막 기록이고, 그 뒤 "Must·Should 없음" 리뷰는 기록에 없습니다.
